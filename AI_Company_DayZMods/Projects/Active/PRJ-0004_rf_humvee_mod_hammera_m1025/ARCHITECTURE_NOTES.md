## (а) Действие люка из салона через RF_Humvee.SetActions без цели

**Вердикт:** работает не всегда. Действие появится, только если луч камеры из салона попадает в саму машину. Если смотреть в окно, в открытый люк или на соседний объект, действие пропадёт. Надёжный ванильный способ — регистрировать действие на игроке.

Факты (VERIFIED по скриптам 1.30):
1. `ActionInteractBase.GetInputType()` возвращает `InteractActionInput` (actions/actioninteractbase.c:61-64). Этот ввод наследует `ContinuousInteractActionInput`: DetectFromTarget = true, DetectFromItem = false, DetectFromPlayer = true (actioninput.c:545-571).
2. Список действий собирается из `target.GetObject()`, `target.GetParent()` и самого игрока (actioninput.c:371-390). Действия машины попадают в список только тогда, когда машина является целью или её родителем.
3. Цель задаёт `ActionManagerClient.FindActionTarget()`: первая цель из `m_Targets`, а если целей нет, то пустой `ActionTarget(null, …)` (actionmanagerclient.c:498-525). `m_Targets.Update()` вызывается каждый кадр (там же, :132-140). Это рейкаст от камеры через `RaycastRVProxy`, игрок исключён (actiontargets.c, около :248-256). Особого случая «своя машина, когда игрок внутри» нет: Transport/IsInVehicle встречаются только в расчёте приоритетов (actiontargets.c:510, :528).
4. В ванили так не делают:
   - двери из салона (`ActionOpenCarDoors`/`ActionCloseCarDoors`: CCTNone, CanBeUsedInVehicle, HasTarget; actions/interact/vehicles/actioncardoors.c:20, :115-123) регистрируются в `PlayerBase.SetActions(out TInputActionMap)` (entities/manbase/playerbase.c:1713-1715, рядом `ActionGetOutTransport` на :1728);
   - `CarScript.SetActions` (entities/vehicles/carscript.c:2313-2318) добавляет только внешние двери (курсор) и `ActionSwitchLights`;
   - `ActionSwitchLights` работает из машины благодаря своему вводу `ToggleVehicleLightsActionInput` (actionswitchlights.c:16). Этот ввод при `IsInVehicle()` принудительно делает целью транспорт (actioninput.c:849-895). Наше действие использует обычный InteractActionInput, такой подстановки у него нет.
5. Маска условий добавляет `ACM_IN_VEHICLE` при `GetCommand_Vehicle()` (actionbase.c, около :878-880), поэтому `CanBeUsedInVehicle() = true` обязателен. У нас он есть.

Риски прежнего кода (до T-0053: InVehicle-действия на `RF_Humvee.SetActions`):
- R1 (главный). Доступность зависит от направления взгляда и от того, пересекает ли луч из салона View/Fire Geometry нашей модели. Попадание луча изнутри замкнутого компонента — ГИПОТЕЗА. На некоторых местах действия может не быть совсем.
- R2. Если в списке есть действия с целью, список строится по ним (actioninput.c:398 и далее). ГИПОТЕЗА: действие без цели в этот момент не показывается. С ванильными дверями из салона то же самое, это допустимо.
- R3. Если зарегистрировать действия и на машине, и на игроке, одно и то же действие попадёт в список дважды. Регистрировать нужно в одном месте.
- Сервер: условие проверяется по `player.GetCommand_Vehicle()`, а не по цели от клиента. Подделка цели ничего не даёт.

**Исправлено в T-0053 (BUG-0008), компиляция NOT RUN.** В RF_HumveeHatch.c:
- `RF_Humvee.SetActions` (строки 15-23) оставляет на машине только Outside-действия;

Почему выбрана перегрузка с картой (VERIFIED): `PlayerBase.InitializeActions` вызывает `SetActions(m_InputActionMapControled)` (entities/manbase/playerbase.c:1780), а `SetActions()` без параметров пустой и оставлен «для совместимости» (:1747-1749).

Условия (ActionRFHatch.c, логика не менялась, обновлён только комментарий в строке 2):
- `RF_GetHumveeFromVehicle` берёт машину из `player.GetCommand_Vehicle().GetTransport()`, а не из цели. Это тот же путь, что у ванильных дверей из салона (actioncardoors.c, ActionCondition);

Оставшиеся риски:

## (б) Новый формат сохранения люка (BUG-0005, T-0050)

Блок пишется в конце записи машины, после `super.OnStoreSave`:
- v0 (старые сборки): `bool open`;
- v1 (сейчас): `bool open`, `int RF_HATCH_STORE_MAGIC` (1380337748 = 0x52464854, «RFHT»), `int RF_HATCH_STORE_VERSION` (1).

Почему bool идёт первым, а не метка: у Serializer есть только `Read/Write/CanRead/CanWrite`, перемотки нет (VERIFIED: scripts/1_core/proto/serializer.c:55-61). Поэтому прочитать int, а потом «передумать» и прочитать bool нельзя. При таком порядке v0 совпадает с началом v1 по байтам, и старые записи читаются тем же первым `Read(bool)`, что и раньше. Не нужна гипотеза о том, совместимы ли bool и int по размеру в потоке.

Чтение (`RF_HatchReadStore`): `super.OnStoreLoad` = false → false, как раньше. Наши данные машину не удаляют никогда (OnStoreLoad возвращает true).

| Запись | Что читаем | Итог |
|---|---|---|
| без мода люка | Read(bool) не удался | закрыт, как раньше |
| v0 | bool прочитан, Read(int) не удался | состояние из сохранения, как раньше |
| v1 | метка и версия совпали | состояние из сохранения |
| v1, версия > 1 (новая сборка → откат) | метка совпала, хвост не читаем | состояние из сохранения (bool не меняется по договорённости) |
| после bool чужие байты (сменился набор модов) | метка не совпала или версия < 1 | закрыт и предупреждение `[RF_Humvee_Hatch]` в script.log |

Оценка:
- Совместимость со старыми сохранениями: полная, если верна гипотеза H1.
- Защита от чужих байтов: для v1 надёжная, случайное совпадение метки маловероятно (порядка 2^-32). Для v0 (bool без метки) чужие байты отличить нельзя. Последствие безвредно: неверное положение люка, машина остаётся.
- Откат на старую сборку: старый код прочитает bool, 8 байт хвоста останутся непрочитанными (H1).

Гипотезы (нужен эксперимент):
- H1. Данные каждой сущности лежат отдельным ограниченным блоком: `Read` за концом блока возвращает false, непрочитанный хвост движок пропускает, при следующем сохранении запись собирается заново. Косвенно это подтверждают допускающие ошибку чтения в ванили (`if (!ctx.Read(x)) x = 0;` в EntityAI.OnStoreLoad, scripts/3_game/entities/entityai.c:2978-2995) и прежнее поведение мода. Если H1 неверна, ни одна схема с добавлением данных в OnStoreSave не безопасна, и тогда нужно отдельное хранилище (свой файл JSON на сервере по persistent ID).
- H2. Если после Hatch чтение продолжит другой `modded class RF_Humvee`, то на записях v0 наш лишний `Read(int)` съест его байты. В нашей семье модов таких классов нет: RF_Humvee.c не переопределяет OnStore*, у RF_Humvee_Desert тело пустое. Правило: будущие данные RF_Humvee добавляются только в этот блок после версии.
- H3. `ctx.Write` локальной переменной int пишет 4 байта int (поэтому метка передаётся через локальные переменные, а не литерал в `void`-параметр).
- Параметр `version` у OnStoreLoad — это версия хранилища игры (ваниль сравнивает его, например, с 143 в entityai.c:2981), а не наша. Мы его не используем.

Сценарий проверки у заказчика (сервер с `-dologs -adminlog -scriptDebug=true`, клиент с тем же `-mod`):
1. На старой сборке (bool без метки) поставить 2 машины RF_Humvee: у первой люк открыт, у второй закрыт. Дождаться сохранения (или выключить сервер штатно).

3. Поменять состояния (открыть люк второй, закрыть первой), сделать рестарт. Состояния сохранились, машины на месте.
4. Открыть люк первой, остановить сервер, снять только аддон RF_Humvee_Hatch (RF_Humvee оставить), запустить. Машины на месте, крышка в положении по умолчанию. Подождать сохранения мира, остановить сервер.

## Место стрелка в люке на будущее (T-0039, только идея)

- В ванили DayZ нет стрельбы из транспорта: у мест экипажа нет оружейного режима. Это гипотеза по отсутствию такого кода, её проверит T-0039.
- Вариант 1, «пассажир в люке» без стрельбы: пятое место экипажа (прокси crew в P3D, класс места в `Crew` config.cpp, скриптовые проверки мест: доступность места, анимация, проход через двери), стоящая поза в проёме. Средняя сложность, без новых сетевых рисков.
- Вариант 2, «встать в люк» со стрельбой: сервер высаживает игрока из места и крепит его к точке на крыше как обычного пешего (связь через иерархию объекта). Высокий риск: рассинхрон при движении, урон и падения, выход и смерть в люке. Нужен эксперимент T-0039, сначала только на стоящей машине.
- Вариант 3, «стрелок на крыше»: стоять на крыше при открытом люке (Roadway LOD уже есть, 2 грани), стрелять только на стоянке. Самый дешёвый, работает сейчас.
- Во всех вариантах положение люка остаётся источником истины на сервере. Новые сохраняемые поля добавляются в блок v2 после версии, по правилу из раздела (б).
